# 11 - Validation Protocol and Paper Plan

## 1. The rules that make results trustworthy

Fix these before looking at any result. Deciding them afterwards is how honest
people accidentally produce unpublishable work.

### Splits

- **Time-based, by `started_at`.** Earliest 70 percent train, next 15 percent
  validate, final 15 percent test.
- **Never random split.** Reactor condition, fouling and operator practice all
  drift. A random split leaks the future into the past and inflates every metric.
- The test split is opened **once**, at the end. Every tuning decision uses the
  validation split only.
- Additionally report `GroupKFold` grouped by `machine_id`, which answers the more
  industrially interesting question of whether a model fitted on two reactors
  transfers to a third.
- `split_manifest.json` records every `batch_key` by split. Without it no number is
  auditable.

### Things that must be decided before looking at results

| Decision | Fix it to | Why it matters |
|---|---|---|
| Fault matching window | 120 minutes | Decided afterwards, it becomes a free parameter that manufactures lead time |
| `T_ref` for severity index | Swept on **train only**, reported | Sweeping on all data is leakage |
| Kinetics `k0`, `Ea` fitting data | **Train only** | These are fitted to maximise correlation with the target, so fitting on all data guarantees an optimistic result |
| Mass-balance exclusion threshold | `closure_error_pct < 0` excluded, `> 5` flagged | Tuning the exclusion rule after seeing results is selecting the data to fit the conclusion |
| Minimum points for a cooling fit | 8 | |
| Cooling fit rejection threshold | `r_squared < 0.9` | |

### Reporting rules

- **`n` appears beside every metric.** With about 100 batches, a metric without n is
  meaningless.
- Confidence intervals on every headline metric, by bootstrap over held-out batches.
- MAE in yield **percentage points** as the headline, because a plant operator can
  interpret it directly. R² is secondary and is easy to inflate with a wide target range.
- Every figure regenerated by `make reproduce`. No hand-edited numbers, ever.
- **Negative results are reported.** A failed RQ1 or a negative lead time is a real
  finding about the limits of sparse industrial telemetry, and the field needs it.

## 2. Answering each research question

### RQ1, identifiability

> Can effective thermal parameters be identified from ~4-minute telemetry with no
> measured heat input?

| Output | Form |
|---|---|
| Primary | Distribution of `tau_cool_min` per machine: median, IQR, coefficient of variation |
| Fit quality | Histogram of `r_squared` across cooling fits, plus convergence rate |
| Physical check | `tau_cool` against `feed_mass_kg` scatter with regression. A positive slope confirms the charge mass is entering `C_eff` as physics requires |
| Consistency check | `tau_h` from heating against `tau_cool` from the same batch |
| Cross-validation | Model `dTr/dt` against the panel's own `roh_c_per_min` |

**Success:** CV within a machine below 0.3, and a significant positive
`tau_cool` versus `feed_mass_kg` slope.

**If it fails:** report it. High CV means 4-minute telemetry does not pin down
thermal parameters at batch level, which is a useful and publishable limit
statement. Investigate whether CV drops when restricted to fault-free batches with
clean sampling, and report that conditional result.

**The interesting upside:** if `tau_cool` predicts `feed_mass_kg` well, the model can
infer charge mass from the cooling curve, which means a plant without a weighbridge
could estimate its charge from a thermocouple. That is a stronger practical result
than anything else here, and it is worth a dedicated figure if it holds.

### RQ2, yield prediction

> Do thermal-severity features predict yields better than feedstock information alone?

Report a full ablation, held-out, per target:

| Feature set | Oil MAE (pp) | Carbon MAE (pp) | Steel MAE (pp) |
|---|---|---|---|
| B0, global mean | | | |
| B1, `feed_mass_kg` only | | | |
| B2, Block A, feedstock only | | | |
| A + B, add thermal severity | | | |
| A + B + C, add model-derived | | | |
| A + B + C + D, add pressure | | | |

**Success:** A+B+C beats B2 on oil yield by more than B2's standard error.

**The negative control:** steel yield should show **no** improvement from thermal
features, because steel content is a feedstock property not a process outcome.
Report this explicitly as a validity check. If thermal features "predict" steel,
there is a leakage bug, and finding it is more important than any other result on
the page.

Also report prediction-interval coverage: nominal 80 percent against empirical.
Undercoverage is common and must be stated rather than quietly ignored.

### RQ3, fault detection lead time

> Do model residuals cross a detection threshold earlier than the panel's alarms?

| Output | Form |
|---|---|
| Primary | Lead-time distribution: median, IQR, histogram, with the 4-minute resolution floor marked on the axis |
| Detection quality | Precision, recall, F1 against panel labels on held-out batches |
| False alarms | False alarms per batch and per operating hour |
| Curves | ROC and precision-recall over the threshold sweep |
| Detector comparison | EWMA against CUSUM |
| Per fault type | Separate results for `choke_emergency` and `gas_passage_choke` |

**`pressure_sensor_error` is analysed separately**, or excluded with a stated reason.
A thermal residual detector has no physical mechanism for anticipating an instrument
fault, and including it would pad the event count while diluting the result.

**Success:** positive median lead time with a false alarm rate low enough to be
usable, roughly under one per batch.

**Be rigorous about the trap here.** A detector tuned for maximum lead time will
fire constantly and achieve excellent lead time while being useless. Always report
lead time and false alarm rate **together**, in the same table. Never quote lead
time alone.

State the event count prominently. With roughly 14 faulted batches across the
dataset, all conclusions here are tentative and must be labelled as such.

### Simulation accuracy, supporting result

On held-out batches:

- Trajectory RMSE and MAE for `tr_c`, in degC
- Phase duration errors, in minutes, per phase
- Total batch time error, in minutes, against a mean-duration baseline
- Yield errors, in percentage points

The headline figure of the whole paper: simulated against measured trajectory for a
single held-out batch, with phase bands, measured as discrete points and simulated as
a continuous line.

## 4. Paper outline

Target: a process-engineering or applied-energy venue, or a digital-twin and
smart-manufacturing venue. Decide by where the tyre-pyrolysis literature actually
sits, which needs a real literature search. **Do not pick a venue from memory.**

**Title, in the honest shape:**
"A data-driven digital shadow for industrial batch tyre pyrolysis: reduced-order
thermal identification, yield prediction, and early fault detection from sparse plant
telemetry"

**Abstract.** Problem, the sparse-telemetry constraint stated up front as the
challenge, method, the three results with numbers, the limitation of sample size.

**1. Introduction.** Waste tyre pyrolysis context. Why plants are instrumented for
monitoring rather than modelling. The gap: digital twin literature assumes dense,
rich instrumentation that real plants in developing markets do not have. Contribution
list.

**2. Related work.** Tyre pyrolysis kinetics and yields. Reduced-order and lumped
thermal modelling. Digital twin taxonomies, citing Kritzinger et al. (2018) for the
model-shadow-twin distinction and using it to position this work precisely as a
shadow. Residual-based fault detection in process industries. The gap: sparse
industrial telemetry rather than lab or richly instrumented pilot data.

**3. Plant and data.** The three reactors. Instrumentation as it actually is. Sampling
cadence and its consequences. Temperature quantisation. Available history. The Excel
batch log and its closure characteristics. Figures F1 to F3, F18. **Be generous with
detail here.** The data's limitations are the paper's context, and hiding them invites
the reviewer to find them.

**4. Method.** Batch segmentation. Thermal model and the identification order, with
the reasoning for starting from unforced cooling. Kinetics. Features. Yield models
and baselines. Fault detector. Model-based interpolation, which doubles as the 3D
visualisation mechanism.

**5. Results.** RQ1, RQ2, RQ3, then simulation accuracy. Every table carries n.

**6. The digital shadow implementation.** The 3D visualisation, with the argument
that matters: model-based interpolation is not cosmetic, it is a necessary consequence
of the sparse cadence, and the visible divergence between projection and the next real
sample **is** the fault signal. The visualisation is the model's output rendered.
Figures F19, F20.

**7. Limitations.** State these plainly and first, not buried.
- Roughly 100 batches, about 14 with faults. All conclusions are tentative.
- No measured heat input. `Q_H` is an effective lumped parameter, not a fuel rate.
- Single lumped zone. One sensor per vessel, so no spatial resolution is claimed.
- 4-minute cadence, 1 degC quantisation. No dynamics faster than a few minutes.
- `cp_charge` assumed from literature, not identified.
- `Ts` and `Pr` models are empirical correlations, not physics.
- Gas yield mostly unmeasured, so closure error mixes gas, moisture and measurement error.
- Five to six weeks of history only. No seasonal or degradation effects.
- Single plant, three reactors, one feedstock. Generalisation untested.
- One-way data flow. This is a shadow, not a twin.

**8. Twin-readiness path.** What additional instrumentation would close each gap, in
priority order. This is the section that turns limitations into a research agenda and
makes the paper a natural PhD proposal foundation.

**9. Conclusion.**

## 5. Consent and ethics

Non-negotiable before submission:

- **Written data-use consent from Plant Operator**, covering the telemetry, the
  batch log, and publication. Email is sufficient; get it in writing.
- Agree with them what may be published: absolute yields and feed masses may be
  commercially sensitive. Offer to normalise yields, anonymise the company, or both.
  Ask before assuming.
- The data statement must describe how data was obtained, including that telemetry was
  collected by automated reading of the operations panel with the operator's
  permission. Do not obscure this.
- Name the panel vendor only if they consent.
- If any co-authorship expectation exists on the plant side, settle it in writing
  early. This is the single most common cause of a finished paper never being submitted.

## 6. Beyond the paper

Two things this work is unusually well suited to, worth planning for from the start
rather than retrofitting:

**A PhD proposal.** A working digital shadow on real industrial data, with honest
limitations and a clearly argued instrumentation roadmap, is a substantially stronger
application artefact than a literature-based proposal. Section 8 of the paper is
effectively the proposal's research agenda. Groups working on process systems
engineering, circular economy, or industrial digitalisation are the natural targets.

**Plant value, which is also the strongest evidence in any application.** If the fault
detector genuinely gives even eight to twelve minutes of warning on a gas passage
choke, that has real operational value, and a letter from the plant saying so is worth
more than another figure. Deploy it, let it run, and collect that evidence.
